01 — start here

The spine

If you remember one picture, make it this one. Every other table in the schema attaches somewhere along this chain.

Why lessons stores course_id as well as module_id

It is redundant — you could always reach the course through the module. It is carried anyway because "every lesson of this course, in order" is the most-run query on the platform, and a trigger refuses any row where the two columns disagree. Denormalisation with a guard, not a shortcut.

02 — the thing that trips people up

Where the foreign keys stop

In MySQL a schema is a database, so the per-service split is seven databases on one server. Every real foreign key lives inside one of them; every arrow that crosses a boundary is just a column holding an id.

MySQL would enforce these. We chose not to.

InnoDB supports foreign keys across databases on the same server — this is not a limitation we ran into. A foreign key across a service boundary means those two services can never be moved onto separate servers, which is the whole point of splitting them. The price is that "does this instructor exist?" is now an application check, and applications forget. tests/verify.sql re-checks the integrity that constraints no longer can.

04 — it clicks here

Follow one action

Sam finishes lesson 5. One request through the gateway, and here is every row that moves — in order.

Upsert progress.lesson_progress
Matched on (user_id, lesson_id). seconds_watched increases by the reported delta, last_position_seconds is overwritten, and state becomes 'completed'. A completed lesson is never demoted just because someone rewatched part of it.
Update progress.enrolments.last_lesson_id
This is what "continue where you left off" reads on the next visit.
Call progress.refresh_enrolment_rollup()
Recounts the completed detail rows, recomputes progress_percent, and flips state to 'completed' if every lesson is done. Steps 1 to 3 run in one transaction, so no reader ever sees an updated lesson row beside a stale summary.
Maybe insert progress.certificates
Only on the transition into 'completed' — on the edge, not every time a finished course is touched again.
Emit to analytics.events — and do not wait
Fire-and-forget. A learner finishing a lesson must not fail, or even slow down, because the Analytics Service is having a bad day. The cost is that events can be lost — which is exactly why nothing authoritative is ever reconstructed from the event stream.
